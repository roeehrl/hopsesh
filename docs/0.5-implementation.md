## Implemented foundation

- `hopsesh runtime observe`: a one-shot local JSON snapshot without state writes,
  account registration/login probing, native-fork adoption, movement marks or agent
  launches. It works without a GUI or a persistent runtime.
- `hopsesh runtime observe --watch`: a local foreground headless observer. One shared
  engine coalesces filesystem changes and performs fallback reconciliation (default
  one minute, configurable from five seconds to one day). It does not receive transfers.
- Immutable subscriber snapshots have an epoch, sequence, attempt/observation times,
  expiry, retained data on failure, explicit errors and sleep/resume invalidation.
  Replay and extra subscribers do not renew freshness or create polling loops.
- Bounded filesystem watches do not follow directory symlinks or read contents.
  Missing roots watch their nearest existing parent; overflow/coverage failures are
  reported. Fallback reconciliation covers missed notifications and process exits.
- Profile-scoped session keys preserve identical vendor IDs in separate roots.
  Registration bindings remain cached metadata, never a fresh login assertion.
- Unverified native-parent metadata is explicitly marked; passive collection never
  constructs a causal family by native ID or title alone. The next lineage tests must
  cover partial/empty Codex fork proof and exact declared inherited boundaries.
- Automated race tests exercise event storms, single-flight collection, suspended
  work, stale results, cancellation, source errors and slow clients. Read-only tests
  compare filesystem trees and deny module writes/execution/termination. The CLI
  scenario runs in the existing Linux/macOS/Windows scenario suite.

No GUI observer is replaced yet: it depends on the ongoing 0.4 integration. The
CLI's `--watch` lifetime is the calling process, with no service registration or IPC
listener. This is useful independently and is also the shared-engine test harness.

## Remaining implementation order and release gates

1. Runtime namespace/singleton locking; private Unix/Windows IPC; CLI detection,
   verified app installation and common validated settings with concurrent updates.
   Test no-display machines, owner death/restart, cancellation, permission denial,
   stale clients, conflicting writers, and install rollback.
2. Consume merged 0.4 changes; connect GUI/TUI, terminal events and native sleep/wake
   to the same engine; remove the replaced timer/collector paths. Measure idle
   wakeups and ensure client count does not multiply source work.
3. Implement scoped device enrollment and reviewed encryption, durable operation
   receipts and relay transport through existing plan/apply/undo. Test replay,
   interrupted acknowledgments, rekey/revocation, competing receivers and unknown
   vendor-create outcomes; do not retry an uncertain creation blindly.
4. Implement separate experimental relay/download infrastructure, quotas, retention
   and diagnostics. Test proxy POST/GET restrictions, overflow, object expiry,
   disconnected clients and cost bounds before publishing the service.
5. Qualify provider bootstrap/lifecycle in disposable real Claude and Codex cloud
   environments. Then implement supported connectors and capability/fidelity UI.
   Installation or a self-reported session ID cannot prove a live connector's owner.
6. Extend pair/triple matrices plus ordered routes: A→B→A→B→A; Claude→Codex→Claude
   on one machine; A-Claude→B-Codex→A-Claude; A→B→C→A;
   A→B→C→B→C→A→B; parent and fork moved/returned independently; cloud pause,
   rebuild and resumed work. Preserve instruction files, capacity safeguards,
   branch independence, causal receipts and counts at every hop.

Provider qualifications, signed native builds, hosted staging checks and final
release publication remain separate gates. Fake tests cannot qualify a real
provider's startup callback, proxy policy or transcript fidelity.
